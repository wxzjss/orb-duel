# GDD · 五模式流转规则（v2.0 新建）

> ⚠️ **v3.0 DEPRECATED 标注（主理人裁定）**：「联机挑战 / 联机boss / 终极boss」三模式及其服务端幽灵池随 v3.0 联机改版**整体作废**（用户指令：删除联机挑战与联机类boss挑战，替换为「联机对战」局域网实时对战——见 modes.md 文末 v3.0 节与 architecture-v3.0-patch.md）。仍然有效：单机挑战、挑战自我、单机boss 三模式，及通用对局结算规则（§3）与 Recorder 全局化（§8）。

## 1. 概述
**「一份操作记录（replay）」是全游戏唯一资产货币**：轨迹 Float32Array + charge/guard 事件（现有 Recorder 格式直接复用）。五个模式 = 同一资产在不同存储池中的进/抽/替/晋/删规则差异。

## 2. 总表

| 模式 | 存储位置 | 池上限 | 进入（怎么来） | 抽取（怎么打） | 替换 | 晋级 | 删除 |
|---|---|---|---|---|---|---|---|
| 单机挑战 | 无持久化（流程产出） | - | 主菜单直入 | 固定：教学关→镜像关 | - | 镜像关胜利 replay 流向挑战自我首关种子 / 联机池播种 | - |
| 挑战自我 | localStorage | 每关 1 个，关数随进度增长 | 见 §4 阶梯规则 | 按当前关顺序挑战 | 被击败 1 次 → 替换为击败者 replay | 累计打败玩家 20 次 → 移入单机boss池 | 20 次晋级即离开本池（槽位由第 20 个受害者 replay 顶替） |
| 单机boss | localStorage | 无上限（顺位排列） | 挑战自我晋级追加 | 按关卡顺位挑战（保守口径：仅第 1 关起顺打，见歧义 #6） | 不替换（计数制） | 无 | 被击败 20 次 → 删除，后续关顺位前移 |
| 联机挑战 | 服务端共享池 | 100 | 池内随机抽 1 | 随机 1 条 | 被打通 1 次 → 原地替换为打通者 replay | 累计打败玩家 1000 次且从未被打通 → 晋级联机boss池 | 晋级即离开本池（腾出 1 席） |
| 联机boss | 服务端共享池 | 1000 | 池内随机抽 1 | 随机 1 条 | 不替换（计数制） | 累计打败玩家 1000 次 → 晋级终极boss顺位队列 | 被击败 20 次 → 永久删除 |
| 终极boss | 服务端共享顺位队列 | 无上限 | 队列头顺位挑战（全服同队头） | 仅队列头 1 条 | 不替换 | 无 | 被击败 1000 次 → 永久删除，下一顺位解锁 |

## 3. 通用对局结算规则（所有模式共用）
1. 每场对局**无论胜负**，Recorder 都产出玩家完整 replay（录制窗口从开局面到玩家死亡/对手死亡帧——工程侧需将录制扩展到败局，见 §8 依赖）。
2. **DRAW（同帧对撞同 tick）= 无效对局**：不产 replay、不计任何计数、不触发替换（保守口径，见歧义 #4）。
3. 计数口径统一见 progression.md；本地池（挑战自我/单机boss）计数在本地权威计算，但结构与服务端一致。

## 4. 单机挑战（v1 流程 + 播种职责）
- 流程不变：教学关（木桩）→ 镜像关。
- 镜像关胜利 → 玩家 replay 产生，两路去向（自动，无需玩家操作）：
  a. **挑战自我首关种子**：若挑战自我存档为空（首次游玩），此 replay 写入挑战自我第 1 关。
  b. **联机池播种**：若服务端联机池 <100，此 replay 自动上传为池条目（计数归零）——解决联机池"空池无人可打"自举问题（见歧义 #1）。

## 5. 挑战自我（本地幽灵阶梯）
- **阶梯结构**：第 N 关存恰好 1 个 replay；关卡随进度解锁（第 N+1 关在第 N 关有占位幽灵后开放挑战）。
- **首进无存档**：引导先完成单机挑战（教学关→镜像关），镜像关胜利 replay 自动存为第 1 关。
- **占位规则（第 N+1 关初始幽灵）**：你击败第 N 关幽灵的那一刻，你的胜利 replay 同时成为第 N+1 关的初始占位幽灵——"想走得更深，先打败刚刚的自己"。此后第 N+1 关被击败 1 次即替换、累计 20 胜即晋级，与其他关一致。
- **替换**：当前关幽灵被玩家击败 1 次 → 该关占位替换为玩家的胜利 replay（旧幽灵消失，只保留一个）。
- **晋级**：某关幽灵累计打败玩家 20 次 → 该 replay 移入单机boss池（追加为最新关，见 §6），同时该挑战自我关槽位被"第 20 次被它打败的那名玩家的 replay"顶替。
- **20 次口径**：是"该幽灵打败玩家的次数"累计，跨多次挑战累计，不清零（被击败替换时才重置——新幽灵从 0 计）。

## 6. 单机boss（本地晋级池）
- 挑战自我每产生一个 20 胜幽灵 → 追加为单机boss第 K 关（K=当前池大小+1，"初始为第一关，往后延顺"）。
- 每关 boss 计数：被挑战成功数（0→20，满即删除该关）、已打败玩家数（仅计数，无上限）。
- 删除后**顺位前移**：第 3 关被删 → 原第 4 关变第 3 关，各关计数随条目走（不属于关卡位）。
- 不替换：boss 被玩家击败只 +1 被挑战成功数，幽灵本体保持不变（与挑战自我"败即替换"形成对比——boss 更硬）。

## 7. 联机挑战 / 联机boss / 终极boss（服务端权威，细则见 progression.md）
- **联机挑战**：开始时随机抽 1 条（服务端抽，返回条目快照+条目 ID）；胜利 → 上报"打通条目 X"→ 服务端将该条目原地替换为玩家 replay（幂等，见 progression.md §4）；失败 → 上报"被条目 X 击败"→ 该条目 已打败玩家数 +1；条目达 1000 且从未被打通 → 晋级联机boss池。
- **池补充规则**：池 <100 时，新产生的失败操作 replay 自动插入（用户原文"不足100个也会记录玩家失败操作"）；池 ≥100 时停止一切插入（替换与晋级仍进行），直到池 <100。玩家胜利操作通过"替换"进入池。
- **联机boss**：随机抽 1 条；被击败 20 次 → 永久删除；打败玩家 1000 次 → 晋级终极boss队列尾部。两条阈值独立计数，**先到先处理**。
- **终极boss**：全服唯一队列头可挑战；被击败 1000 次 → 删除，队列下一顺位成为新头，全服解锁。已打败玩家数仅计数无阈值行为。

## 8. 依赖（工程侧需知）
1. **Recorder 扩展**：录制窗口覆盖所有对局（含败局、含各模式），对局结束产 replay 对象 {traj, events, meta:{mode, result}}。
2. **幽灵来源抽象（ServeProvider）**：现有 GhostPlayer 回放器不变，喂入端从"教学关录制"泛化为"任一 replay 对象"，教学关录制只是 provider 之一。
3. **服务端 API 需求**（语义级，实现归技术侧）：pool_count / serve_random(pool) / report_result(entryId, win|lose, replay?) / queue_head(ultimate)。计数与替换全部服务端权威，客户端仅展示——契约详见 architecture-v2.0-patch.md §3。
4. localStorage 结构：{entries:[{replay, beatenPlayers, challengedSuccess}], unlockedLevel}（键名以架构前缀 'gd.<mode>.' 为准）。

## 9. 边界情况（模式级）
1. 挑战自我阶梯玩家打到第 N 关后离开，下次进入从第 N 关继续（进度=最远解锁关）。
2. 单机boss池只有第 1 关时被删 → 池空 → 主菜单单机boss按钮灰显。
3. 联机挑战对局中断线 → 作废不计数（服务端以 report 为准，未 report 即无效）。
4. 玩家 replay 隐私：replay 仅含操作数据，无身份信息（lean 不做昵称系统，见歧义 #7）。
5. 挑战自我 20 胜晋级与"被击败替换"同帧竞争不存在（本地单线程，逐局结算）。
6. 服务端同一玩家高频刷分：同一玩家对同一条目连续败北照常计数（"已打败玩家数"语义自洽，不做防刷）。

## 10. 验收标准
- [ ] 总表 6 列规则逐模式可追溯实现，无未定义流转。
- [ ] 挑战自我首进→单机挑战→回填第 1 关→挑战→替换→20 胜晋级→单机boss追加全链路可跑通。
- [ ] 联机池 100 上限的停止插入/恢复插入行为正确（构造 99/100/99 场景）。
- [ ] 终极boss删除后队列顺位前移且全服可挑战新头。

# v3.0 增量 · 联机对战（局域网实时对战，取代联机三池）

> 【主理人裁定 · 架构优先】本节与 architecture-v3.0-patch.md 的冲突以架构为准：①B2「同步模型：双端确定性模拟（lockstep-ish）」**作废** → 采用 ADR-008 权威服务端 + 60Hz 快照直发 + 客户端插值；②B5「断线判负」**作废** → 采用 30s 内重连恢复座位、期间座位由内置 AI 托管；③联机 AI 席驱动位置以 ADR-009 为准（AI 席跟随该座位所在客户端，输入与人类同通路），A1 节「房主端驱动」相应修正。

## A. 座位与对局形态
- **P1、P2 两个对战席位**：每个座位 = human 或 AI（房间内切换，仅房主、未开局时）。真人对真人 / 真人对 AI / AI 对 AI 由座位组合自然覆盖。
- **观战席位**：上限 8，只收对局状态流不可输入。
- AI 座位：由入座该席位的客户端运行 OrbAI（见 ai-interface.md），产生的输入与人类输入走完全相同的网络通路（服务端零区分，公平性结构性保证）。
- **联机对战纯 PVP，不带幽灵**：Recorder/GhostPlayer 不进联机对局（幽灵玩法留在单机模式）。

## B. 对局流转
1. **B1 房间生命周期**：WAITING（配置座位）→ COUNTDOWN(3s) → PLAYING（60Hz 权威模拟+快照广播）→ ENDED（结算）。
2. **B2 同步模型**【已作废，以 ADR-008 为准】：~~双端确定性模拟 + 输入转发~~ → 权威服务端模拟，客户端收快照插值渲染。
3. **B3 胜负与计分**：三局两胜由 Room 层计分（p1Wins/p2Wins），单局 Match 不感知场次；每局结束回到 COUNTDOWN。
4. **B4 结算**：ENDED 态显示比分，「再来一局」（房主可触发）回到 COUNTDOWN，「退出房间」回大厅。
5. **B5 断线处理**【已修正，以架构 §1.4 为准】：~~判负~~ → 断线座位 30s 内由内置 AI 托管并保留重连恢复；超 30s 观战席位释放、对战席位保持 AI 托管直到房主改配。

## C. 边界情况
1. 观战者中途加入 → 从当前快照起播，不要求回放历史。
2. AI 座位的客户端断线且该座位为 AI → 无影响（AI 托管逻辑在内置白名单，服务端可直接接管）。
3. 手机玩家：触屏控件 + 横屏加入联机对战，行为与桌面一致（见 mobile.md）。
4. 单机三模式（单机挑战/挑战自我/单机boss）零网络依赖，与联机完全隔离。

## D. 验收
- [ ] 真人对真人 / 真人对 AI / AI 对 AI 三种座位组合各跑通一场完整对局。
- [ ] 观战席位收到与对战者一致的快照流且无输入通道。
- [ ] 断线重连 30s 内恢复座位、AI 托管无缝交接。
- [ ] 联机对局全程零 Recorder/GhostPlayer 路径（幽灵玩法隔离断言）。

# v4.0 小改 · 录制与联机协议适配

1. **Recorder 事件类型**：`charge` → **`blade`**（dirAngle=准星方向）；新增 **`hammer`**（同）；`guard_begin/guard_end` 不再产生（历史 replay 回放时静默跳过）。录制格式/采样/循环/镜像规则（x'=1280−x、dirAngle'=π−dirAngle）全部不变。
2. **联机 input 帧协议**：`guardHeld` 字段 → **`hammer`**（bool/坐标）；`click0/chargeHeld` → `blade`。传输层（WebRTC DataChannel、权威端=房主）不变。
3. **幽灵武器复刻**：幽灵按事件类型执行刀/锤（参数同玩家），锤秒杀/刀三击杀判定对幽灵同等生效——被自己教出来的锤处刑是本版本核心叙事时刻。
4. 座位/配对/观战/单机模式流转全部不变。

## 验收补充
- [ ] 含 blade+hammer 事件的完整对局录制→镜像回放闭环跑通。
- [ ] 联机双端新旧字段协议一致性（同版本客户端）。
